## Overview [[icons]]

This is the first lab in a four-part series building a complete PXE network boot infrastructure from scratch. Before clients can boot over the network, they need a reliable DNS server to resolve hostnames in the internal lab domain. In this lab, I install and configure BIND (Berkeley Internet Name Domain) on Server 1 to serve a private `example.vm` zone, handle DNS forwarding to Google's public resolvers for external queries, and lock down `/etc/resolv.conf` so the server always queries itself.

Every subsequent lab depends on this one. DHCP will advertise this DNS server to clients, FTP will be referenced by hostname, and the PXE bootloader relies on name resolution working correctly across the network.

**What this lab builds:**

```
Server 1 (192.168.56.106)
└── DNS - named  (port 53)
    ├── Authoritative for: example.vm
    ├── Forwarders: 8.8.8.8, 8.8.4.4
    └── Serves: 192.168.56.0/24
```

**Prerequisites:**
- Server 1 freshly installed with AlmaLinux 9
- Root or sudo access
- `enp0s8` connected to the host-only network
- `enp0s3` has internet access via NAT

## Part 1 - Configure a Static IP on Server 1

Before setting up DNS, Server 1 needs a permanent IP address so clients always know where to find it. A DHCP-assigned address would change on reboot and break everything downstream.

I also set the hostname here so logs and DNS records are consistent throughout the series.

```bash
hostnamectl set-hostname server1.example.vm
```

### Check the current interface configuration

```bash
ip a s
```

The server has three relevant interfaces: `enp0s3` (NAT, internet access), `enp0s8` (host-only, target for the static IP), and `enp0s9` (a second host adapter used for SSH access during the lab).

```
[root@localhost ~]# ip a s
1: lo: ...
2: enp0s3: ... inet 10.0.2.15/24 ...
3: enp0s8: ... (no inet address yet)
4: enp0s9: ... inet 10.0.0.184/24 ...
```

### Set the static IP on enp0s8

```bash
nmcli connection modify "Wired connection 1" \
  ipv4.method manual \
  ipv4.addresses 192.168.56.106/24 \
  ipv4.dns 127.0.0.1 \
  connection.autoconnect yes

nmcli connection down "Wired connection 1"
nmcli connection up "Wired connection 1"
```

The DNS is pointed at `127.0.0.1` so the server queries itself once BIND is running. `connection.autoconnect yes` ensures the static IP persists after a reboot.

Verify the address was assigned:

```bash
ip a s enp0s8
```

```
3: enp0s8: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ...
    link/ether 08:00:27:42:bc:22 brd ff:ff:ff:ff:ff:ff
    inet 192.168.56.106/24 brd 192.168.56.255 scope global noprefixroute enp0s8
       valid_lft forever preferred_lft forever
```

The absence of the word `dynamic` in the output confirms this is a static assignment.

#### Troubleshooting - Unknown Connection Name

When I first tried to modify `enp0s8` directly, NetworkManager returned an error because the connection profile had a different name:

```
Error: unknown connection 'enp0s8'.
```

Running `nmcli connection show` revealed the actual profile name was "Wired connection 1". Using that name in the modify command resolved the issue.

### Prevent other interfaces from overriding DNS

NetworkManager collects DNS information from every active interface and writes it all into `/etc/resolv.conf`. Since `enp0s3` and `enp0s9` get their DNS from DHCP (VirtualBox NAT), they would overwrite the `127.0.0.1` entry I just set. I need to suppress that on both interfaces.

```bash
nmcli connection modify enp0s3 ipv4.ignore-auto-dns yes
nmcli connection down enp0s3 && nmcli connection up enp0s3

nmcli connection modify "Wired connection 2" ipv4.ignore-auto-dns yes
nmcli connection modify "Wired connection 2" ipv6.method disabled
nmcli connection down "Wired connection 2" && nmcli connection up "Wired connection 2"
```

#### Troubleshooting - IPv6 DNS Leaking into resolv.conf

After setting `ipv4.ignore-auto-dns yes` on `enp0s3`, I still saw IPv6 nameserver entries appearing:

```
# Generated by NetworkManager
nameserver 2001:558:feed::1
nameserver 2001:558:feed::2
nameserver 127.0.0.1
```

The fix was to also disable IPv6 DNS and IPv6 autoconfiguration on the external interfaces. The `ipv4.ignore-auto-dns` flag only suppresses IPv4 DNS pushed via DHCP - IPv6 SLAAC/DHCPv6 pushes its own DNS separately and requires `ipv6.ignore-auto-dns yes` or disabling IPv6 entirely on those interfaces.

After applying the fix to both `enp0s3` and `enp0s9`:

```
# Generated by NetworkManager
search example.vm
nameserver 127.0.0.1
```

## Part 2 - Install and Start BIND

BIND is the industry-standard open-source DNS server. On AlmaLinux 9, the package split changed from older RHEL versions, so both the server and client tools need to be installed explicitly.

```bash
dnf install -y bind bind-utils
```

- `bind` - the DNS server daemon (`named`)
- `bind-utils` - client tools including `dig` and `nslookup`

#### Troubleshooting - Package Download Fails Before DNS Is Configured

During this step I hit a chicken-and-egg problem: `dnf` needs to resolve `mirrors.almalinux.org` to download the package, but DNS isn't configured yet, so the download fails:

```
Error: Error downloading packages: Curl error (6): Couldn't resolve host name for
https://mirrors.almalinux.org/mirrorlist/9/appstream
[Could not resolve host: mirrors.almalinux.org]
```

The fix is a temporary entry in `/etc/resolv.conf`:

```bash
echo "nameserver 8.8.8.8" >> /etc/resolv.conf
```

This lets the server reach the internet for the initial install. Once BIND is running, NetworkManager will overwrite `resolv.conf` back to `127.0.0.1` on the next interface cycle.

### Enable and start the service

```bash
systemctl enable named
systemctl start named
systemctl status named
```

BIND starts in caching-only mode by default, which is fine for now. You may see `network unreachable` messages in the status output for IPv6 root servers - these are harmless and expected in a NAT environment.

```
named.service - Berkeley Internet Name Domain (DNS)
     Loaded: loaded (/usr/lib/systemd/system/named.service; enabled)
     Active: active (running) since Tue 2026-06-02 23:22:07 EDT; 14ms ago
   Main PID: 12876 (named)
```

## Part 3 - Configure BIND (named.conf)

By default BIND only listens on `127.0.0.1`, which means clients on the host-only network cannot reach it. The main configuration file controls what networks BIND listens on, which clients are allowed to query it, and where it forwards external queries.

```bash
vi /etc/named.conf
```

### Update the listening interface and query permissions

Inside the `options { }` block, change the following:

**Before:**
```
listen-on port 53 { 127.0.0.1; };
listen-on-v6 port 53 { ::1; };
allow-query { localhost; };
```

**After:**
```
listen-on port 53 { any; };
listen-on-v6 port 53 { none; };
allow-query { localhost; 192.168.56.0/24; localnets; };
```

`any` opens BIND to all IPv4 interfaces. IPv6 is disabled since the lab uses IPv4 only. The `allow-query` directive is broadened to include the entire host-only subnet plus `localnets` (which covers all directly attached networks automatically).

### Enable DNS forwarding

Still inside `options { }`, add:

```
forwarders { 8.8.8.8; 8.8.4.4; };
forward only;
```

`forward only` tells BIND not to attempt its own recursive lookups. All external queries are delegated to Google's resolvers. This keeps the server simple and avoids issues with root hint resolution in a lab NAT environment.

### Final options block

```
options {
    listen-on port 53 { any; };
    listen-on-v6 port 53 { none; };
    directory       "/var/named";
    dump-file       "/var/named/data/cache_dump.db";
    statistics-file "/var/named/data/named_stats.txt";
    memstatistics-file "/var/named/data/named_mem_stats.txt";
    allow-query     { localhost; 192.168.56.0/24; localnets; };
    recursion yes;
    forwarders { 8.8.8.8; 8.8.4.4; };
    forward only;
    dnssec-validation yes;
};
```

### Validate and restart

`named-checkconf` validates the configuration file syntax. No output means it is clean:

```bash
named-checkconf
named-checkconf -v   # -v shows the BIND version
systemctl restart named
```

```
[root@localhost ~]# named-checkconf
[root@localhost ~]# named-checkconf -v
9.16.23-RH
```

### Verify BIND is listening on all interfaces

```bash
ss -ltnp | grep named
```

> **AlmaLinux 9 note:** `ss` replaces `netstat` here. The `net-tools` package is not installed by default on AlmaLinux 9.

```
LISTEN 0  10  192.168.56.106:53   0.0.0.0:*   users:(("named",pid=12912,fd=45))
LISTEN 0  10       10.0.2.15:53   0.0.0.0:*   users:(("named",pid=12912,fd=41))
LISTEN 0  10       127.0.0.1:53   0.0.0.0:*   users:(("named",pid=12912,fd=36))
```

Port 53 now shows on `192.168.56.106`, confirming clients on the host-only network can reach it.

## Part 4 - Configure the Firewall

AlmaLinux 9 ships with `firewalld` active. Port 53 must be opened explicitly or DNS queries from other machines will be silently dropped.

```bash
firewall-cmd --permanent --add-service=dns
firewall-cmd --reload
firewall-cmd --list-services
```

```
[root@localhost ~]# firewall-cmd --list-services
cockpit dhcpv6-client dns ssh
```

`dns` appears in the list, confirming both TCP/53 and UDP/53 are open.

## Part 5 - Create a Forward Lookup Zone

The forward lookup zone is what makes `server1.example.vm` resolve to an IP. Without this, BIND would handle external queries via the forwarders but have no knowledge of the internal `example.vm` domain.

### Add the zone declaration to named.conf

```bash
vi /etc/named.conf
```

Append after the existing `include` lines at the bottom:

```
zone "example.vm." {
    type master;
    file "db.example";
    allow-update { none; };
};
```

`type master` makes this server authoritative for the zone. `allow-update { none; }` disables dynamic DNS updates, which keeps the zone file static and predictable.

### Create the zone file

```bash
cd /var/named
cp named.empty db.example
chgrp named db.example
```

The zone file is stored in `/var/named/`, which the `named` process has access to. Copying from `named.empty` gives the correct base format. The `chgrp named` command is important - without it, BIND cannot read the file and the zone will fail to load.

```
[root@localhost named]# ls -l db.example
-rw-r-----. 1 root named 152 Jun  2 23:39 db.example
```

### Edit the zone file

```bash
vi /var/named/db.example
```

Replace the contents with:

```
$TTL 3H
$ORIGIN example.vm.
example.vm.     IN SOA  server1.example.vm. root.example.vm. (
                        1       ; serial
                        1D      ; refresh
                        1H      ; retry
                        1W      ; expire
                        3H )    ; minimum TTL

example.vm.     NS      server1.example.vm.
server1         A       192.168.56.106
```

| Record | Purpose |
|--------|---------|
| `SOA` | Start of Authority - identifies the primary nameserver and admin contact |
| `NS` | Name Server record - delegates queries for `example.vm` to `server1` |
| `A` | Address record - resolves `server1.example.vm` to `192.168.56.106` |

The serial number (`1`) should be incremented every time the zone file is modified so secondary servers (if any) detect the change and sync.

### Validate and reload

```bash
named-checkzone example.vm /var/named/db.example
named-checkconf
systemctl restart named
```

```
[root@localhost named]# named-checkzone example.vm /var/named/db.example
zone example.vm/IN: loaded serial 1
OK
```

Confirm the zone loaded from the BIND log:

```bash
cat /var/named/data/named.run | grep "zone example"
```

```
zone example.vm/IN: loaded serial 1
```

## Part 6 - Test DNS Resolution

### Test the A record

```bash
dig server1.example.vm @127.0.0.1
```

The `@127.0.0.1` directs the query explicitly at the local BIND instance, bypassing any system resolver settings:

```
;; ANSWER SECTION:
server1.example.vm.     10800   IN      A       192.168.56.106

;; Query time: 4 msec
;; SERVER: 127.0.0.1#53(127.0.0.1)
```

### Test the NS record

```bash
dig -t NS example.vm @127.0.0.1
```

```
;; ANSWER SECTION:
example.vm.             10800   IN      NS      server1.example.vm.

;; ADDITIONAL SECTION:
server1.example.vm.     10800   IN      A       192.168.56.106
```

The additional section automatically includes the A record for the name server itself, which is correct behavior.

### Test DNS forwarding (external domain)

```bash
dig www.google.com @127.0.0.1
```

```
;; ANSWER SECTION:
www.google.com.         196     IN      A       142.251.150.119
www.google.com.         196     IN      A       142.251.151.119
...

;; Query time: 120 msec
;; SERVER: 127.0.0.1#53(127.0.0.1)
```

Running the same query a second time returns a much lower query time (typically under 5ms), confirming BIND is caching the results from the upstream forwarders.

### 5. Prevent enp0s3 from overriding DNS

The external interface (enp0s3) uses DHCP and may push its own DNS into `/etc/resolv.conf`, which would override your local DNS server. Disable that:

## Part 3 — Configure BIND (named.conf)

By default BIND only listens on `127.0.0.1`, which means other machines can't reach it. We need to open it up to the internal network.

### 1. Edit the main config file

```bash
vi /etc/named.conf
```

### 2. Update the listening interface

Find this block inside `options { }` and change it:

**Before:**

```
listen-on port 53 { 127.0.0.1; };
listen-on-v6 port 53 { ::1; };
```

**After:**

```
listen-on port 53 { any; };
listen-on-v6 port 53 { none; };
```

This makes BIND listen on all IPv4 interfaces and disables IPv6 listening.

### 3. Allow queries from the internal network

Still inside `options { }`, find and update `allow-query`:

**Before:**

```
allow-query { localhost; };
```

**After:**

```
allow-query { localhost; 192.168.56.0/24; localnets; };
```

> `localnets` covers all networks directly attached to the server's interfaces. Including `192.168.56.0/24` explicitly adds clarity and a safety net.

### 4. Enable DNS forwarding

Add these two lines inside `options { }` (before the closing `};`):

```
forwarders { 8.8.8.8; 8.8.4.4; };
forward only;
```

- `forwarders` — upstream DNS servers (Google's public DNS)
- `forward only` — BIND will not do its own recursive lookups; it delegates everything to the forwarders

### 5. Final options block (for reference)

Your `options { }` block should look like this:

```
options {
    listen-on port 53 { any; };
    listen-on-v6 port 53 { none; };
    directory       "/var/named";
    dump-file       "/var/named/data/cache_dump.db";
    statistics-file "/var/named/data/named_stats.txt";
    memstatistics-file "/var/named/data/named_mem_stats.txt";
    allow-query     { localhost; 192.168.56.0/24; localnets; };
    recursion yes;
    forwarders { 8.8.8.8; 8.8.4.4; };
    forward only;
    dnssec-validation yes;
};
```

### 6. Validate the configuration

```bash
named-checkconf
```

No output means the config is valid. Add `-v` to see the BIND version:

```bash
named-checkconf -v
```

```
[root@localhost ~]# named-checkconf
[root@localhost ~]# named-checkconf -v
9.16.23-RH
[root@localhost ~]#
```
### 7. Restart BIND

```bash
systemctl restart named
```

### 8. Verify BIND is now listening on all interfaces

```bash
ss -ltnp | grep named
```

You should see port 53 on `192.168.56.106`, `10.0.2.x`, and `127.0.0.1`.

## Part 5 — Create a Forward Lookup Zone

This zone lets clients resolve hostnames like `server1.example.vm` to an IP address.

### 1. Add the zone to named.conf

```bash
vi /etc/named.conf
```

Scroll to the bottom of the file, **after** the `include` lines, and add:

```
zone "example.vm." {
    type master;
    file "db.example";
    allow-update { none; };
};
```

> The trailing dot in `"example.vm."` denotes the root of the DNS hierarchy. Omitting it is valid in modern BIND but including it is good practice.

### 2. Navigate to the zone file directory

```bash
cd /var/named
```

### 3. Copy the empty zone template

```bash
cp named.empty db.example
```

### 4. Set correct ownership

```bash
chgrp named db.example
```

The file should be readable by the `named` group but only writable by root:

```bash
ls -l db.example
```

Expected: `-rw-r-----. 1 root named ...`

```
[root@localhost ~]# vi /etc/named.conf
[root@localhost ~]# cd /var/named
[root@localhost named]# ls
data  dynamic  named.ca  named.empty  named.localhost  named.loopback  slaves
[root@localhost named]# cp named.empty db.example
[root@localhost named]# chgrp named db.example
[root@localhost named]# ls -l db.example
-rw-r-----. 1 root named 152 Jun  2 23:39 db.example
[root@localhost named]#
```
### 5. Edit the zone file

```bash
vi /var/named/db.example
```

Replace the contents with:

```
$TTL 3H
$ORIGIN example.vm.
example.vm.     IN SOA  server1.example.vm. root.example.vm. (
                        1       ; serial
                        1D      ; refresh
                        1H      ; retry
                        1W      ; expire
                        3H )    ; minimum TTL

example.vm.     NS      server1.example.vm.
server1         A       192.168.56.106
```

**Record breakdown:**

|Record|Purpose|
|---|---|
|`SOA`|Authoritative info — primary server and admin email|
|`NS`|Points to the name server for this domain|
|`A`|Resolves `server1.example.vm` → `192.168.56.106`|

> **Serial number:** Increment this every time you change the zone file. Slave servers use it to detect updates.

### 6. Validate the zone file syntax

```bash
named-checkzone example.vm /var/named/db.example
```

Expected output:

```
zone example.vm/IN: loaded serial 1
OK
```

### 7. Validate named.conf again

```bash
named-checkconf
```

### 8. Restart BIND

```bash
systemctl restart named
```

```
[root@localhost named]# vi /var/named/db.example
[root@localhost named]# named-checkzone example.vm /var/named/db.example
zone example.vm/IN: loaded serial 1
OK
[root@localhost named]# named-checkconf
[root@localhost named]# systemctl restart named
[root@localhost named]#
```
### 9. Check the logs for zone load confirmation

```bash
cat /var/named/data/named.run
```

Look for a line like:

```
info: zone example.vm/IN: loaded serial 1
```

```
[root@localhost named]# cat /var/named/data/named.run | grep "zone example"
zone example.vm/IN: loaded serial 1
[root@localhost named]#
```
